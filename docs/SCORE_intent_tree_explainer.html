SCORE · Architecture note · August 2026

One query, one rule: intent trees

A redesign of SCORE's intent layer. Instructors carve nested sets of intents inside four fixed query types, and every student query routes to exactly one rule — overlap between intents becomes impossible by construction.

1 · The problemIndependent classifiers overlap

In the current design, each intent is an independent classifier applied to every query in the log. Two intents can both claim the same query, so the system needs dedicated machinery to resolve conflicts — an overlap queue, pairwise tie-breakers, ownership decisions. That machinery is the main source of UI and logic complexity, and an unresolved overlap at chat time means the student silently gets no rule at all.

2 · The modelFour types, then nested sets

Step 1 — every query gets exactly one type. A multi-class classifier assigns each query to one of four fixed activity types: Planning, Translating, Reviewing, Drafting. Queries mixing several activities tie-break to Drafting. Since a message never changes, its type is computed once, ever.

Step 2 — inside a type, instructors carve sets. Each type is a root set with its own editable default rule (a rule is a complete system prompt). An intent is a set created inside an existing set — directly under the type, or nested inside another intent. There is no separate "base prompt": whatever no intent captures is handled by the type's own rule.

3 · RoutingFirst match wins, children before parents

The tree is an authoring model. At evaluation time it compiles to a flat if / else-if chain: each set's subsets are checked before the set itself, and siblings follow creation order (adjustable in the UI). The first matching set's rule applies; the type's default rule is the final else.

# the tree compiles to a chain: subsets before their parent,
# sibling subtrees in creation order (adjustable)
route(query):
    T = type_of(query)              # one of the four types (Fig. 2)
    for set in chain(T):           # e.g. [Citation, Proofreading, Feedback]
        if set.matches(query):      # each set judged independently
            return set.rule
    return T.default_rule           # the final "else" — never no rule

4 · RulesNew rules start as copies

When an instructor creates a set, its rule is seeded as a copy of the enclosing set's rule — they edit only what should differ ("same as Reviewing in general, but for citation questions, point to the style guide instead of fixing it"). Rules diverge independently after creation; each rule stays one complete, self-contained prompt with no hidden layers underneath.

5 · PropertiesWhy this shape

  • Exactly one rule, alwaysOverlap cannot occur, so there is no conflict-resolution UI to learn — the queues, tie-breakers, and ownership decisions of the previous design disappear structurally.
  • Familiar mental modelSets-within-sets and if/else-if are shapes non-technical instructors already understand; the four types give them a scaffold to browse real queries and form intents. (Both informed by our instructor demos.)
  • Reorganizing is freeSet membership is judged per set, independently. Moving a set, nesting it, or reordering siblings changes only the routing walk — no re-classification is needed.
  • Every query gets a real ruleThe type's own rule is the final else, so there is no hidden fallback prompt and no query that silently receives nothing.
  • Robust to judge noiseBecause parents are not gates, a single misjudgment on a broad set cannot make its subsets unreachable; the confident, specific match still wins.

6 · StatusOpen items we are validating

  • Type-classifier accuracy. An earlier 4-type classifier reached 79.2% agreement with human coding — but that was measured before pasted material was substituted with placeholders (e.g. [OWN DRAFT]). We are re-evaluating on human-labeled data with substitution applied, since a type error cannot be recovered downstream.
  • The Drafting tie-break. How often do real queries mix activities across types? We can measure this directly from our request-level dissection of the logs.
  • Workbench redesign. The intent-editing workbench is being rethought around the tree: candidate queries scoped to the enclosing set, sibling-shadowing indicators, and a diff view against the seed rule.
