**문서 지위.**
- 이 문서는 Simple 버전의 **목적과 목표 설계**를 기술한다. 특정 시점 코드에 대한 델타 명세가 아니다.
- **코드가 진실이다.** 본문·힌트에서 언급하는 기존 기제·명칭은 08-05 as-built 문서 기준이라 **최신이 아닐 수 있다.** 재사용 힌트로만 취급하고, 현행 코드와 다르면 현행 코드에서 대응물을 찾아 이 문서의 **의미론**을 충족하도록 구현한다.
- **풀 버전은 삭제하지 않는다** — Simple은 별도 조건 쌍으로 추가된다. (연구 리포 README/SoT 등록은 방향 확정 후.)
- 표기: **[확정]** = 연구자 결정 · **[제안]** = 구현 세부 제안(합리적이면 채택, 현행 코드에 더 나은 길이 있으면 대체 가능) · **[확인]** = 연구자 확인 대기. 태그 없는 서술은 [확정]에 준한다.

## 0. 목적

08-18·08-20 파일럿의 관찰: AI 보조 저작 기능(후보 생성·수정 제안·교정 흡수 등)이 지연·불안정·불투명으로 저작 경험을 지배했고, 참가자는 AI 제안에 의존하면서 디버깅에는 실패했다. 그 결과 "intent–rule **표현**의 효과"와 "AI **도구** 마찰"이 데이터에서 분리되지 않았다.

Simple 버전은 이 교락을 제거한다. **조작 변인은 설정의 표현 하나다: monolithic prompt vs intent–rule.** 사용자가 모든 설정 텍스트를 직접 쓰고, 시스템의 임무는 두 가지뿐이다:

1. 사용자가 쓴 설정이 무엇을 하는지를 **빠르게** 보여준다.
2. 그 외에는 **아무것도 하지 않는다.**

연구 어휘로, Baseline은 When-Then이 합쳐진 하나의 프롬프트에 대한 시뮬레이션 하나이고, SCORE는 두 시뮬레이션의 분리다 — **When 시뮬레이션**(라우팅: 어떤 쿼리가 어느 intent에 걸리나)과 **Then 시뮬레이션**(응답: 걸린 rule이 무슨 응답을 낳나). 이 분리가 사용자에게 무엇을 가능하게 하는지가 연구 질문이므로, 시스템은 분리를 **사실대로, 빠르게** 보여주는 것까지만 한다.

> 스터디 재설계는 연구 리포에서 진행 중이다. 이 문서는 시스템 선행 구현을 위한 스펙이다. **스터디 절차(블록 테스트 등)는 기존 스터디 버전의 방식을 그대로 쓴다 [확정]** — Simple을 위한 신규 연구자 도구는 현시점 불필요.

## 1. 설계 원칙

1. **LLM 역할 제한.** LLM은 딱 두 곳에만 쓴다: ① **응답 생성**(= 챗봇 행동 그 자체), ② **intent 소속 판정**(= 라우팅, SCORE만). 설정 텍스트(프롬프트·intent description·rule)는 **오직 사용자가 쓴다.** 예외는 **라벨**뿐이다: 버전 이름·한 줄 변경 요약(§3.3), 그리고 **이름 없이 만들어진 intent의 title(§5.3, 08-21 추가)**. 셋 다 같은 기준을 통과한다 — ① 판정에도 응답에도 들어가지 않아 챗봇 동작을 바꾸지 않고(title은 intent별 버전 축에서도 일부러 빠져 있다: 버전은 (definition, rule) 쌍이다) ② 이미 쓰인 것을 읽기만 하며 ③ **비동기·비차단**이고 실패하면 빈칸이 남을 뿐이다. 라벨이 아닌 것(설정 텍스트)은 여전히 오직 사용자가 쓴다. 구현 중 애매한 판단이 생기면 이 질문으로 판정한다: **"이 기능이 사용자 대신 설정을 써 주거나 해석해 주는가? — 그렇다면 Simple에 없다."**
2. **속도 최우선.** 저장 → 반영이 빨라야 한다. 작은 수정 → 확인 루프를 부담 없이 반복할 수 있는 것이 이 버전의 존재 이유다. 정량 목표 §6.
3. **원페이지 대시보드.** 워크벤치·생성 모달 없음. 모든 저작과 확인이 3컬럼 대시보드 안에서 일어난다.
4. **경고하지 않는다 [확정 — 지도교수 요청 일반화].** 시스템은 사실(이 쿼리가 어디에 적용되는가 · 무엇이 바뀌었는가)을 **중립적으로 표시**하고, 경고·진단·해석(⚠ 아이콘류)을 하지 않는다. 문제의 발견과 판단은 사용자의 몫이며, 그 과정 자체가 관찰 대상이다.
5. **Baseline = intent가 0개인 SCORE [제안].** 구조적으로 Simple-Baseline은 "루트 rule 하나만 있는 Simple-SCORE"와 동형이다. 한 코드베이스에서 condition으로 렌더 분기하는 구현을 권장한다.

## 3. 공통 사양

### 3.1 레이아웃

3컬럼: **좌 = 설정 + 버전 리스트** | **중 = 쿼리 리스트** | **우 = conversation viewer**.

- 중앙: **전체 쿼리 flat 리스트가 기본** [확정]. 타입 섹션·필터·검색 없음. 정렬 고정(참가자 간 동일한 시작 화면). 쿼리 수가 수백이어도 성립해야 하므로 리스트 가상화 [제안].
- 우측: 선택 쿼리의 대화 뷰어. 응답은 "현재 보는 버전" 기준(§3.4).

### 3.2 데이터셋 [확정]

- **현행 데이터셋 구성을 그대로 쓴다 — 축소 없음.** 타입은 UI에 어떤 형태로도 노출하지 않는다(데이터 준비·분석의 어휘로만 남는다).
- 따라서 시스템 설계는 **쿼리 수 N에 무관하게** 성립해야 한다: 전량 사전 생성을 전제하지 말 것(§6).

### 3.3 버전 모델

- **버전은 Save만 만든다 [확정 — 08-21 개정].** Apply는 효력만 갖고 버전이 되지 않는다 — 최신 save 뒤의 **작업 행(working row) 하나**에 쓰고, 다음 apply가 그 행을 덮어쓴다. 여섯 개 문안을 시험하면 여섯 행이 아니라 한 행이 남고, 참가자가 읽는 번호는 **간직할 만하다고 판단한 지점의 개수**가 된다. Save는 버전을 쓰고 작업 행을 치운다(그 내용이 방금 버전이 되었으므로).
  - **다만 intent별 히스토리는 apply에도 쌓는다 [08-22 재개정].** 방금 1분 걸려 쓴 intent의 히스토리가 `0`이라고 말하는 건 그것에 대한 틀린 답이다. 대신 각 행이 **`unsaved`**(최신 save보다 뒤에 쓰인 것)를 달아 무엇이 효력만 있는지 말한다. 설정 레벨의 버전 번호는 여전히 save만 센다.
  - **apply가 기록에서 사라지는 것은 아니다** — 모든 쓰기는 `simple_version_save` 이벤트에 무엇이 바뀌었는지(필드 단위)를 남기고, 분석이 읽는 것은 그쪽이다. 다만 스냅샷 전문은 남지 않으므로, **중간 apply 시점의 설정 전문을 사후 재구성할 수는 없다 [확인]** — 측정 대상은 마지막 save이므로 문제없다고 보지만 연구 쪽 확인 사항으로 남긴다.
- **Revert는 직전 Save로만 [확정 — 08-21].** 갈 곳이 거기밖에 없다. 작업 행 하나를 지우면 끝이고, 버전이었던 적 없는 행이라 보존할 히스토리도 없다. 위치는 **Version history 헤더 옆** — 되돌아갈 대상이 나열된 자리다. 위 행의 세 동사(Apply · Save · Undo/Redo)는 *지금 쓰이고 있는 것*에 작용하고, Revert는 그걸 버린다.
- **컬럼 아래 상시 바는 없다 [확정 — 08-21].** Save·Revert는 열려 있는 에디터 안에 있고, 미저장 상태에 대한 안전장치는 이미 헤더의 **"I'm done"**이 갖고 있다 — 미저장이면 그 자리에서 *"Save and finish"*를 제안한다(§blocked). 컬럼 밑에 상주하는 두 번째 장치는 같은 말을 한 번 더 하는 것이었다. **양쪽 arm의 에디터가 같은 동사 행을 갖는다** — 두 조건은 설정이 *무엇인가*에서 갈리지 다루는 방법에서 갈리지 않는다.
- **동사는 자리를 지키고 흐려진다 [확정 — 08-21].** Apply는 상자 안에 이미 적용된 것 말고 다른 게 없으면, Save는 마지막 저장 이후 바뀐 게 없으면 비활성. 타이핑 중에 버튼 줄의 모양이 바뀌면 방금 누르려던 것이 움직이고, 흐려진 Apply는 "적용할 게 없다"고 말하지만 사라진 Apply는 아무 말도 하지 않는다.
- **전역 스냅샷 [제안].** 버전 = 설정 전체의 스냅샷(Baseline: 프롬프트 하나 / SCORE: 루트 rule + 모든 intent의 description·rule + 트리 구조·순서). 버전 축은 하나다 — 전역 선택·뷰어 드롭다운과 일관되게.
- **Deploy = 최종 Save [확정 — 08-21 개정].** 브리핑이 처음부터 *"When you feel it's ready, deploy it."* 라고 말해 왔는데 보드에는 그 동사가 없었고, "I'm done"이 **마지막 save를 조용히 답으로 간주**하고 있었다 — 어느 save를 말하는지는 아무도 묻지 않았다. Deploy는 별도의 라이브 사본을 만드는 게 아니다(보드는 늘 최신 쓰기로 답해 왔다). **"내가 한 save들 중 이것"이라는 선언**이고, 그게 없으면 측정 대상은 "우연히 마지막으로 저장한 것"이 된다.
  - 한 번 누르면 **적용된 것을 저장하고 그것에 도장을 찍는다** — 미저장 상태로 배포하는 것과 화면보다 오래된 버전을 배포하는 것 둘 다 "이게 당신이 의도한 것인가"에 대한 틀린 답이다.
  - **"I'm done"은 배포 뒤에만 나온다** (풀 버전과 같은 순서). 배포 후 더 손대면 게이트가 다시 올라가고(`changed since deploy`) "Deploy and finish"를 제안한다.
  - **측정 대상은 배포본**(`getSimpleDeployed`)이다. 재배포는 허용·예상되며 선언을 현재로 옮긴다. 옛 행의 도장은 남아서 언제 무엇을 딛고 섰는지가 트레일에 보존된다. `simple_deploy`로 로깅.
- **복원 = 롤백 [확정].** 과거 버전으로 복원하면 **이후 버전들은 사용자 관점에서 소실**되고 그 버전이 최신(tip)이 된다. 따라서 **"마지막 버전 = 최종 상태"가 항상 성립**한다 — 별도 Deploy 개념 없음. 스터디의 사후 절차(블록 테스트)는 마지막 버전을 쓴다.
  - [제안] DB에서는 소실 버전을 soft-delete로 보존한다(연구 데이터·과정 분석용). 사용자에게는 보이지 않는다.
- **LLM 버전 이름 [확정 — 08-21 개정: apply에도].** 저장·적용 모두에 이름 + 한 줄 변경 요약을 경량 LLM이 생성한다. 원래는 save에만 붙였으나, 뷰어가 적용 상태도 고를 수 있게 되면서 이름 없는 행이 생겼다. **비동기·비차단** [제안]: 저장은 LLM과 무관하게 즉시 성공, 이름은 도착하면 채움(그 전엔 "v{N} · {시각}" 폴백). 실패해도 저장은 유효.
- [제안] 버전 리스트에서 항목 선택 시 설정 텍스트의 전신 diff 열람 — 복원 판단의 재료.

### 3.4 버전 열람 의미론 [확정]

- **전역 버전 선택**(좌측 버전 리스트) = 대시보드 전체가 그 버전 기준으로 표시(응답·소속·트리).
- **로컬 드롭다운** = **응답 자체에 붙인다 [08-21 개정].** rule이 적용되는 건 선택된 그 한 턴이지 대화 전체가 아니다 — 컬럼 헤더에 두면 대화 전체에 대한 설정으로 읽힌다. 풀 버전의 `ResponseVersionBar`가 같은 자리에 같은 이유로 있다. 문장형으로 상태를 말한다: *"This reply is under [ ]"* / *"Working out this reply under [ ]"*.
- **"Original (as delivered)" 선택지 [08-21].** 버전이 아니라 별개의 답이다 — 학생이 실제로 받은 응답이고, 어떤 설정으로도 재현할 수 없으며, 나머지를 비교할 유일한 고정점이다. 고르면 왕복 없이 아래 대화의 응답을 그대로 둔다.
- 여기 나열되는 버전은 **모든 버전(apply 포함)이다 [08-21 개정].** 좌측 타임라인은 "어디로 되돌아갈 수 있나"라서 save만 답이 되지만, 뷰어는 "그때 이 답이 어땠나"라서 apply도 똑같이 답이 된다 — intent별 히스토리가 가리키는 지점 대부분이 apply이므로, save만 나열하면 히스토리가 제시하는 wording을 볼 수 없다.
- **모든 버전에 이름을 붙인다(apply 포함) [08-21 개정].** 원래는 save에만 붙였고 근거는 "apply는 어디에도 나열되지 않으니 아무도 안 읽는 문자열에 모델 호출을 쓸 이유가 없다"였다. 뷰어가 모든 moment를 나열하게 되면서 그 전제가 깨졌다 — apply도 골라야 하는 행이 됐는데 혼자 "6h ago"만 적혀 있으면 그 행만 이질적이다. 항목 표기는 **`{이름} · {상대시각}`** — 사람이 훑는 건 이름이고 시각은 같은 일을 한 둘을 가를 때만 쓴다.
- **뷰어 드롭다운에는 `v N`을 쓰지 않는다 [08-21].** 이 화면에서 `v N`은 intent 자기 버전 번호를 뜻한다. 두 체계가 한 이름을 쓰면 "v2를 보고 있는데 v1만 선택 가능"이 된다. 뷰어는 **시각 + 이름**으로 지목한다(시각 표기는 intent 히스토리와 동일한 상대 시각이라 눈으로 맞출 수 있다).
- **기본 rule 그대로면 원본 응답을 보여준다 [08-21].** 적용될 rule이 과제 자체 프롬프트와 글자까지 같다면, 그 프롬프트가 만들어 낸 응답이 이미 화면에 있다. 다시 생성하면 다른 답이 나와서 손대지 않은 설정이 무언가 한 것처럼 보이고, 블록 첫 몇 분 내내 불필요한 생성이 걸린다.
- **우선순위: 전역 > 로컬.** 전역 버전 변경 시 모든 로컬 오버라이드 리셋.
- 과거 버전은 읽기 전용(에디터 잠금 + "이 버전으로 복원" 버튼). 편집은 항상 tip에서.
- 응답 재생성은 lazy + 캐시(§6) — 캐시된 버전 간 전환은 즉시.
- 응답 재생성은 단일 교환 기준의 **지표적(indicative)** 결과임을 UI에 명시(기존 관례 계승).

### 3.5 Pin [확정]

- 쿼리 행의 핀 토글. 핀된 쿼리는 중앙 리스트 최상단 **sticky 섹션**에 상시 노출 — intent 선택·버전 전환과 무관하게 항상 접근 가능.
- 목적: intent를 선택하면 소속 밖 쿼리가 안 보이므로, 밖의 쿼리를 참조하면서 intent를 수정할 수 있게. **Baseline에도 동일 제공**.
- **§5.3의 확인 장치이기도 하다 [08-21].** 쿼리에서 intent를 시작하면 그 쿼리가 자동으로 핀된다 — 선반 행의 소속 칩이 곧 "이번 wording이 그걸 잡았나"의 답이 된다. **이것은 핀에 의미론을 더하는 것이 아니다**: 핀은 여전히 북마크이고, 판정·캐시 키·프롬프트·라우팅에 아무 영향이 없다.
- **의미론 없음 [제안 — 중요].** 핀은 순수 UI 북마크다. 판정·캐시 키·프롬프트·라우팅에 어떤 영향도 없다. (과거 시스템에 존재했던 "pin = 교정" 개념과는 무관한 신규 상태 — 그 기제·테이블을 재사용하지 말 것.)

## 4. Simple-Baseline 사양

- **좌:** monolithic prompt **인라인 에디터** [확정] — 쿼리를 보면서 편집. 아래에 **버전 리스트**(이름 · 요약 · 시각; 클릭 = 전역 선택 → 읽기 전용 열람 + 복원).
- **중:** 전체 쿼리 flat + pinned sticky.
- **우:** 대화 뷰어 + 로컬 버전 드롭다운.
- Save → 새 버전 → 응답은 lazy 재생성(§6).
- Baseline에서 프롬프트 수정은 **정의상 전 쿼리에 적용**된다 — 응답 변경은 항상, 전역으로 일어난다 [확정]. 따라서 행 단위 "변경됨" 표시는 정보가 없어 두지 않는다(모든 행이 항상 해당). 소속 개념이 없으므로 §5.4~5.5(소속 표시·diff)의 대응물도 없다. 이 비대칭 — **SCORE는 국소 변경, Baseline은 전역 변경** — 은 조작 그 자체이므로 UI로 보정하지 않는다.

## 5. Simple-SCORE 사양

### 5.1 구성 리스트 [확정 — 08-21 개정]

- intent는 **평면 순서 리스트**다. **first-match · 배타 소유** 유지, **리스트 순서 = 판정 순서.**
- **중첩 폐지 [확정 — 08-21].** 중첩이 주던 것은 둘뿐이었다: ① 부모보다 먼저 평가됨 ② 조상이 모두 매치한 쿼리만 가져감. ①은 리스트 위치가 이미 준다. ②는 **따로 판정된 두 텍스트 사이의 보이지 않는 AND**여서, definition의 문장만으로는 그것이 무엇을 잡는지 알 수 없고(배포된 챗봇도 문장밖에 못 받는다), 그것이 만드는 유일한 실패 모드(부모가 배제해서 자식이 아무것도 못 가져감)는 **원칙 4가 경고를 금지한 것**이다. 대가: 범위 조건을 사용자가 **글로 써야** 한다 — 원칙 1이 요구하는 바이기도 하다.
- **하나의 else rule, 이름은 "Uncategorized"**: 타입 구분이 사라지므로 루트는 하나. 어떤 intent에도 안 걸린 쿼리의 rule이며, **리스트 맨 아래에 그린다** — 그것이 도달되는 자리다(위에 그려두면 "위에서 아래로 읽는다"는 설명과 그림이 어긋난다).
- **순서 조정(↑↓) 유지 [확정]** — first-match에서 순서는 사용자가 통제해야 할 의미론이다. 평면이 되면서 조정 범위가 리스트 전체로 넓어진다(중첩 시절에는 형제 그룹 밖으로 못 옮겼다).
- **저장된 중첩 스냅샷은 읽을 때 평탄화한다.** 중첩 스냅샷은 문서 순서(부모 먼저)로 저장되고 **평가는 post-order(자식 먼저)**였으므로, 배열 순서를 그대로 쓰면 중첩 쌍의 우선순위가 뒤집힌다. 옛 평가 순서로 재배열해서 읽는다.

### 5.2 아코디언 에디터 [확정]

- **Save는 Apply 뒤에만 열린다 [08-22].** Save가 간직하는 건 상자 속 글자가 아니라 **효력 중인 것**이라, 적용 안 한 편집이 상자에 있으면 화면과 다른 걸 간직하게 된다. 적용해서 무엇이 됐는지 보고, 그다음에 간직할지 정한다.
- **Version history는 3개까지 보이고 나머지는 펼친다 [08-22].**
- **새 intent는 Save로 태어난다 [08-22].** intent가 존재하게 되는 것은 시도가 아니라 결정이라, 카드가 아무것도 없는 히스토리 대신 **v1**로 열린다. 그 뒤의 편집은 다른 것들과 같은 apply다.
- **중간에 다른 질문으로 옮겨도 생성은 끝까지 간다 [08-22].** 읽는 사람이 떠나면 컨트롤러가 닫히는데, 생성 비용은 어차피 치러진다 — 그래서 밀어 넣기만 멈추고 끝까지 모아서 캐시한다. 다시 그 질문을 열면 재생성이 아니라 캐시 히트다. 닫힌 컨트롤러에 밀어 넣던 것이 `Invalid state: Controller is already closed`의 원인이기도 했다.
- **"최신을 보고 있다"와 "v3로 돌아가 있다"는 다른 상태다 [08-22].** `viewing`은 절대 null이 아니다 — 팁에서는 팁이다. 그래서 뷰어가 그걸 그대로 버전 번호로 쓰자 두 상태가 구분되지 않았고, 뒤에 있는 모든 것이 후자로 읽었다. 대가는 지름길이었다: 룰을 묻지 않고 알아내는 건 팁에서만 허용되므로, 번호가 늘 붙어 있는 동안 보드는 **여는 질문마다 서버에 물었다** — 아무 룰도 안 닿는 질문까지. 화면에 이미 있는 답을 받으려고 자리표시자와 대기를 치른 것이고, 참가자가 본 깜빡임이 이거다. 한 줄이 조용히 비싸게 틀렸으므로 `askedVersionNo`로 빼내 4케이스를 고정했다.
- **어떤 버전에서도 나오지 않은 응답에 버전 번호를 붙이지 않는다 [08-22].** 고른 게 없을 때 최신 버전이 드롭다운의 값으로 서 있어서, 손대지 않은 질문이 "This reply is v1"으로 읽혔다 — v1이 만들었다는 주장인데 실제로 만든 건 과제의 원래 프롬프트다. 이제 **사람이 고른** 버전만 자기 번호를 유지하고, 그 외에 배달된 답이면 "Original (as delivered)"이다.
- **볼 게 하나뿐이면 상자도 없다 [08-22].** 목록은 배달된 답 + moment 하나씩이라, moment가 하나면 "배달된 답"과 "정확히 그걸 만들어내는 버전" 사이의 선택 — 답 하나에 라벨 둘이다. 그럴 때는 `This reply is the one that was delivered.` 한 줄이다. moment가 둘 이상이면 상자가 돌아온다: 옛 버전은 지금 안 잡는 질문을 잡았을 수 있으므로 그때부터 진짜 비교가 시작된다.
- **질문 개수는 어디서나 같은 알약을 쓴다 [08-22].** 개수가 나오는 곳은 네 군데(트리 행, intent 히스토리 행, 스타터 세트, 재사용할 룰)인데 전부 맨숫자였다 — 무엇을 세는지 읽는 사람이 알아내야 했고, 더 나쁘게는 **다 같은 것**이라고 넘겨짚게 했다. 알약(말풍선 아이콘 + 숫자)이 공유하는 부분이다: 이건 지금 보고 있는 로그의 질문 개수다.
- **다만 *무엇을* 세는지는 다르고, 그건 title이 말한다 [08-22].** 트리 행은 **소유**(위 intent들이 가져가고 남은 뒤 이 질문이 최종적으로 가는 곳 — 그래서 합이 로그와 같다), 히스토리 행은 **매치**(위에 뭐가 있든 그 문구가 서술하는 질문 수 — 히스토리가 답하는 질문은 "그 행의 words가 뭘 잡나"이므로). 둘은 한 intent가 다른 intent도 서술하는 질문을 가져가기 시작하는 순간 갈라지고, 그때 같은 숫자처럼 보이면 안 된다. 그래서 `QuestionCount`의 `title`은 **필수**다 — 설명 없는 개수를 막으려고 만든 컴포넌트다.
- **지어낸 예시는 고쳐 쓸 수 있다 [08-22].** 아래 목록이 그것들을 기준으로 정렬되므로, 문구가 마음에 안 들면 지웠다 다시 만들 게 아니라 **고칠 값어치**가 있다 — 모델이 짐작한 "이 범주는 이렇게 들린다"는 출발점이고, 아는 사람은 참가자다. 고치면 **다시 임베딩한다**: 글자는 바뀌었는데 벡터가 그대로면 아무도 못 읽는 것으로 목록을 정렬하게 된다. 로그에서 온 질문 행은 못 고친다 — 거기 적힌 건 학생이 한 말이다.
- **버튼은 자기가 할 일을 말한다 [08-22].** 자리가 남으면 그 자리를 채우니 `Generate examples`, 세트가 차 있으면 쓰여진 것을 전부 갈아치우니 `Update examples`. 한 이름으로는 둘 중 하나가 늘 거짓말이었다.
- **Generate examples는 누르는 동안 일하고 있다고 말한다 [08-22].** 세 개를 지어내는 건 모델 호출이고 — **실측 약 15초**(생성 + 임베딩) — 그동안 목록은 그대로라 아무 일도 안 한 버튼처럼 읽히고 두 번째 클릭을 부른다. 스피너는 Apply처럼 **그 누름에 귀속**된다(모든 쓰기가 공유하는 플래그가 아니라). 도는 동안 버튼은 닫혀 있다.
- **baseline의 Rules 상자도 쓰인 만큼의 크기다 [08-22].** `flex-1 min-h-[24rem]`로 컬럼 높이에 고정돼 있어서, **상자가 자기 안에서 스크롤되고 컬럼도 스크롤되고** 그 아래 버튼은 화면 밖에 반쯤 걸쳐 있었다. score arm과 같은 상자를 쓰되 **천장이 없다** — 이건 룰 하나가 아니라 문서 전체라, 자라는 건 상자이고 스크롤하는 건 컬럼이다. 빈 상태에서는 12줄로 시작한다(이 arm의 일 전부가 그 상자다). 실측: 283px(12줄) → 40줄을 적자 920px, 컬럼이 스크롤되고 상자 안쪽은 `overflow:hidden`, Apply/Save는 컬럼 안에 있다.
- **텍스트 상자는 안에 쓰인 만큼의 크기다 [08-22].** 고정 높이는 두 방향으로 동시에 틀린다 — 한 줄짜리 룰이 여섯 줄짜리 빈 상자에 앉아 있고, 긴 definition은 자기 길이의 1/3짜리 창에서 스크롤되는데 그 아래 빈 상자가 차례를 기다린다. 없을 때 **2줄**, **10줄**까지 자라고 그 뒤로는 스크롤한다(10줄이면 이미 컬럼 대부분이고, 페이지를 먹는 상자는 아래 버튼들을 화면 밖으로 밀어낸다). 상수가 아니라 computed style에서 재므로 타입 스케일을 손으로 맞춰줄 필요가 없다.
- **패딩은 숫자가 아니라 보이는 게 같아야 한다 [08-22].** `px-2 py-1`. `leading-relaxed`가 여분 행간의 절반을 첫 줄 위에, 절반을 마지막 줄 아래에 두므로(이 크기에서 약 4px), 옆과 같은 간격을 남기려면 패딩이 그만큼 작아야 한다. 숫자를 맞추면 글자가 상자 안에서 눈에 띄게 내려앉는다 — 중요한 건 **글자까지의 간격**이고 그게 네 면 모두 8px다. 실측: 글자 위 8.375px vs 옆 8px, 2줄 = 56px.
- **지금 보고 있는 버전 행은 호버를 이겨야 한다 [08-22].** 5% 틴트는 바로 옆에 있는 호버 회색에 졌다. 이제 accent 색을 제대로 쓰고 왼쪽에 2px 바를 세운다. 나머지 행에는 투명 바를 둬서 읽는 위치가 옮겨갈 때 글자가 옆으로 밀리지 않는다.
- **`when` / `then` / `when + then` 표시는 없앴다 [08-22].** ("first"도 같이 — 비교 대상이 없다는 걸 가리키는 라벨은 소식이 아니다.) 그 단어들은 카드 위의 필드 이름인데, 목록을 훑는 사람이 그 대응을 머리에 이고 다니지 않는다 — 시간으로 읽히거나 아무것도 아닌 걸로 읽혔다. **개수가 같은 일을 더 잘한다**: 보드의 나머지가 이미 쓰는 단위이고, 더 많은 질문을 잡는 문구는 넓힌 문구이며, 그 숫자는 트리의 행에서와 여기서 같은 뜻이다.
- **저장 안 한 행도 개수를 갖는다 [08-22].** 저장된 행마다 채워져 있고 맨 윗줄만 비는 열은 열이 없느니만 못하다. 히스토리와 같은 조회다(판정은 definition 텍스트로 키가 걸리므로 읽기 한 번, 판정은 없다). 실측: definition을 넓히자 저장 안 한 행이 11 → **18**로 혼자 움직였고 아래 v1은 11에 머물렀다. 판정이 로그를 한 번 훑기 전에는 0이다.
- **적용본에도 이름을 붙인다 [08-22].** apply는 이미 응답 버전 픽커 때문에 이름이 생성되고 있었다. 그 한 줄이 가장 쓸모 있는 자리가 **저장할지 말지 정하는 행**이다. 이름은 held에 **복사**해 둔다 — 실시간으로 읽으면 옛 행을 보러 간 뒤엔 전혀 다른 변경의 이름이 된다.
- **이름이 도착하는 걸 몇 번 더 기다린다 [08-22].** 이름은 응답 뒤에 best-effort로 쓰이는데(nano 모델로 1~3초), 보드는 판정 중에만 리로드했다. 그래서 같은 apply가 한 번은 "v2 · Refined Complete Text intent", 다음 번엔 맨 "v2"였다 — 판정 루프의 마지막 패스보다 이름이 먼저 왔는지에 달린 문제. 이름 없는 행이 있으면 2.5초 간격으로 최대 8번 더 물어본다.
- **Revert는 되돌아가 본 뒤에만 나온다 [08-22].** 효력 있는 행이 **저장된 행이면서 목록 맨 위가 아닐 때** — 즉 이전 행을 누른 바로 그 상태일 때만이다. 최신에서는 돌아갈 데가 없고, 거기 살아 있는 버튼은 지금 하고 있는 일을 무르라는 제안처럼 읽힌다. (저장 안 한 것을 버리는 건 그 아래 저장본으로 가는 것이고, 그건 그 행에서 누르는 같은 동작이다.) 확인은 취소 가능하다.
- **범위는 설정 전체 [08-22].** 버전은 원래 설정 전체의 스냅샷이라, intent A의 v1로 가면 그 시점 이후 전부가 사라진다. confirm이 그렇게 적는다: "Back to v1, dropping 2 later — the whole setup?"
- **숨김이지 삭제가 아니다 [08-22].** `restoreSimpleVersion`이 이후 config 버전을 `hidden_at`으로 표시할 뿐이고 트레일은 전부 가져간다 — 뭔가 시도했다가 되돌린 것이야말로 RQ1이 원하는 흔적이다. 다만 그 쓰기에 딸린 **per-intent 행은 지운다**: 하나하나가 위 스냅샷에 이미 있는 쌍의 사본이라 트레일이 잃는 게 없고, 남겨두면 마지막 행이 v1인 카드 다음 저장이 v5가 된다. 되돌리면 undo 스택도 비운다 — 그 스텝들이 가리키는 상태는 타임라인에 없고, 되밟으면 방금 일부러 버린 걸 조용히 되살린다.
- **행을 누르면 보드 전체가 그 버전이 된다 [08-22].** 상자에는 그 버전이 하던 말이 차고, 쿼리 리스트는 그 버전이 만든 리스트가 되고, 대화는 그 버전으로 답한다 — 전부 **읽기 전용**이다. 아무것도 쓰지 않는다: 컬럼 위 배너가 어느 버전이 화면에 있는지 말하고, 최신으로 돌아가는 길과 이 버전을 최신으로 만드는 길을 준다. 이 장치(`viewing`/`atTip`/배너)는 이미 있었고 score arm에서만 닿을 길이 없었다.
- **누를 때 적용하던 것은 준 것보다 뺏은 게 많았다 [08-22].** 상자에 있던 걸 덮어썼고, v1을 보러 갔더니 **v1과 똑같은 v3가 생겼다**(적용은 쓰기라서 moment가 생기고 다음 저장 번호를 단다). 밀려난 작업을 붙잡던 장치 한 벌도 함께 사라졌다.
- **저장 안 한 것은 어디서 보든 목록에 남는다 [08-22].** `unsavedSids`가 *보고 있는* 스냅샷 기준으로 계산되고 있어서, v1을 보러 가는 순간 v2(적용만 하고 저장 안 한 것) 행이 사라졌다 — 되돌아갈 길을 쥔 행이 같이 사라진 것이다. 이제 **팁 기준**이다: 누군가 적용해 놓고 저장 안 했다는 건 그 사람 작업에 대한 사실이고, 옛 버전을 본다고 해서 참이 아니게 되지 않는다. 그 행을 누르면 최신으로 — 즉 그 작업이 있는 곳으로 — 돌아온다.
- **Restore / Latest는 히스토리 옆에 있다 [08-22].** 보드를 그리로 옮긴 누름이 있던 자리다. 컬럼 맨 위 배너는 **어디에 있는지만** 말하고, 그에 대해 할 수 있는 두 가지는 읽고 있는 목록 옆에 있다.
- **읽기 전용에서는 `unsaved` 칩을 안 보여준다 [08-22].** 거기서는 저장 안 된 게 없다 — 그 칩이 읽고 있는 건 작업과 저장의 차이가 아니라 **두 버전의 차이**가 된다.
- **Restore도 먼저 묻는다 [08-22].** 이 지점 이후에 저장되거나 적용된 것이 전부 타임라인에서 빠진다(숨김이지 삭제는 아니다). undo 스택도 비운다 — 그 스텝들이 가리키는 상태가 타임라인에 없기 때문이다.
- **Apply는 자리를 잡고, Save가 그 자리를 진짜로 만든다 [08-22].** 적용됐지만 저장 안 된 상태가 히스토리 맨 위에 **다음 저장이 받을 번호**를 달고 앉는다 — `v2 · unsaved`가 Save를 누르면 `v2`가 되고, 그 다음 apply가 v3다. 저장된 것과의 차이에서 파생하므로 자기가 설명하는 저장보다 오래 살 수 없고, 눌러도 아무 일이 없다(이미 적용된 것을 적용하겠다는 버튼은 안 만든다). 세 자리 중 하나를 차지해서 카드 높이는 그대로다. **입력만 한 것에는 행이 생기지 않는다** — 이 행은 *효력 있는 것*에 대한 것이고, 그래서 draft가 아니라 tip 스냅샷을 읽는다.
- **`commit`이 intent 버전을 안 쓰고 있었다 [08-22].** 주석은 "커밋은 이미 효력 있는 상태를 표시할 뿐이라 모든 쌍은 받을 버전을 이미 갖고 있다"고 주장했는데, apply가 일부러 안 쓰기 때문에 거짓이었다. 결과: **보드의 Save 버튼으로 저장한 intent는 만들어질 때의 히스토리에서 영원히 멈춰 있었다** (v1 하나). 지금은 commit과 deploy(최종 save)가 둘 다 기록한다.
- **드롭다운은 위에서 아래로 최신 → 오래된 것, 원본이 맨 끝 [08-22].** `Original (as delivered)`은 "버전 아님" 항목이라 맨 위에 뒀었는데, 그러면 **가장 오래된 답이 가장 새 답 위에** 오고 그 아래로 다시 거슬러 내려간다. 그건 여기서 제일 오래된 것이다 — v1보다 오래됐다, 이 중 아무것도 쓰이기 전에 챗봇이 한 말이니까. 카드 히스토리와 같은 방향이 된다. (전체 방향을 뒤집는 건 검토 후 유지: 카드가 최신 3개만 보여주므로 뒤집으면 접힘이 위로 자라고, 참가자가 실제로 만지는 `current` 행이 버튼에서 멀어진다.)
- **번호는 intent마다 센다 [08-22].** `v1`은 **그 intent의 첫 문구**이고, 보드가 그때까지 세 번을 저장했든 새 intent는 v1에서 시작한다. 카드가 답하려는 질문은 "이 문구가 몇 번째냐"이지 "설정의 몇 번째 저장이냐"가 아니다.
- **설정 전체의 버전은 내부에만 남긴다 [08-22].** undo/redo와 되돌리기가 그 위에서 돈다. 화면에 그 번호가 필요한 자리(읽기 배너, Deploy 상태, 복원 확인)에서는 **"setup 3"** 이라고 부른다 — 서로 다른 사건의 열을 세는 둘이 같은 `v`일 수는 없다.
- **응답의 픽커도 intent 버전이다 [08-22].** 답하는 intent가 가졌던 문구들(v1, v2 — 카드와 같은 번호) + `Now (unsaved)` + `Original (as delivered)`. 고르면 그 문구로 답을 만든다: 라우트가 **행 id**를 받아 서버에서 룰을 읽는다(클라이언트가 룰 텍스트를 부르는 게 아니다). 실측: v2 → v1로 바꾸자 응답이 "Second: …"에서 "First: …"로 바뀌었다.
- **짧은 룰도 상자는 전체 폭이다 [08-22].** 담긴 열이 `items-start`라 폭이 내용만큼으로 줄어서, 짧은 룰이 자기가 설명하는 응답의 절반쯤에서 끊겼다. 실측: 9글자 룰이 503px(응답 폭 471px 이상).
- **Version history는 최근 3개가 그냥 보이고, 헤딩이 나머지를 연다 [08-22].** 접힌 폴드는 안에 뭐가 있는지 안 보이니 열 이유도 안 생긴다 — 히스토리가 접혀 있던 동안 아무도 열지 않았다. 3개는 "내가 어디 있나"에 필요한 만큼(마지막 저장, 그 전, 방향이 보일 정도)이고 높이는 위 버튼 줄 하나 정도다. 3개 이하면 헤딩은 컨트롤이 아니라 그냥 라벨이다 — 열 것이 없는데 달린 셰브런은 없는 것을 약속한다.
- **헤더 줄의 컨트롤은 전부 h-5 [08-22].** 안에 든 글자는 제목보다 작아도 패딩과 테두리는 안 작다 — 그 2px 때문에 Examples 상자가 양옆 두 컬럼보다 높았다. 정렬도 `items-baseline`이 아니라 `items-center`다(베이스라인에 걸면 컨트롤의 디센더가 제목 아래로 내려가 한 픽셀을 더 밀어낸다). 실측: Setup / Examples / Conversation 모두 37px, y=94.
- **블록 종료 게이트가 simple 참가자에게 항상 "아무것도 없다"고 말하고 있었다 [08-22].** `advance`가 `deployStateFor`에 **arm**(`'score'`)을 view 자리에 넘겼다. 배포본이 어느 저장소에 있는지는 **family에 대한 사실**이라, arm을 받은 함수는 "simple 아님"으로 읽고 full 버전 테이블을 뒤져 아무것도 못 찾았다 — 배포를 마친 참가자가 "Nothing has been set up here yet"을 보고 블록을 끝낼 수 없었다. `condition`을 `StudioView`로 타이핑해서 **같은 실수가 컴파일되지 않게** 했다(호출부 전부 검사됨). 실측: WOOK의 1블록이 `{deployed:false,label:null}` → `{deployed:true,label:'v5'}`.
- **거절 문구는 화면에 있는 버튼을 가리켜야 한다 [08-22].** simple 보드의 거절이 "Save your chatbot first"라고 말하고 있었는데, 그건 Deploy 버튼이 생기기 전에 쓰인 문장이다 — 화면에는 있지만 **블록을 끝내는 동사가 아닌 것**을 가리키고 있었다. 잘못된 컨트롤을 가리키는 안내는 없느니만 못하다: 한 번 더 누를 게 남았다가 아니라 **뭔가 잘못됐다**로 읽힌다. 이제 상태마다 다르게 말한다 — 배포 후 변경 / 한 번도 배포 안 함 / 아무것도 안 씀.
- **비활성 버튼도 왜인지 말한다 [08-22].** 비활성 컨트롤은 포인터 이벤트를 안 받으므로 **자기 `title`이 절대 안 열린다** — Apply·Save가 갖고 있던 이유들은 전부 쓰여 있고 한 번도 보인 적이 없었다. 이유를 비활성이 아닌 래퍼에 걸어서 살아 있든 흐려 있든 같게 읽힌다. 상태별로: 쓰기 대기 중 / 효력과 다른 게 없음 / 먼저 Apply해야 함(Save는 *효력 있는 것*을 보관하므로) / 마지막 저장 이후 바뀐 게 없음.
- **`unsaved`는 회색 글자가 아니다 [08-22].** 다음 단계가 읽는 것에 안 들어간 상태라 눈에 띄어야 한다. 히스토리의 `unsaved`와 같은 accent — 알약 배경 + semibold — 이라 보드 전체에서 한 언어다. 경고색(앰버)은 쓰지 않는다: 이건 사실이지 잘못이 아니다(§1-4).
- **Deploy가 곧 블록의 끝이다 [08-22].** 브리핑은 "when you feel it's ready, deploy it"에서 멈추는데, 배포한 *다음* 단계는 따로 찾아 눌러야 하는 두 번째 버튼이었다. 이제 한 번 묻고("This deploys the setup you have now and ends it. …"), 확인하면 배포하고 그대로 다음 단계로 넘어간다. 자기 fetch가 아니라 `PhaseAdvance`를 통한다 — 어떤 단계는 나갈 때 생성 배치가 돌아 화면을 덮어야 하고, **어디로 착지하는지는 한 곳에만 있어야 할 규칙**이기 때문이다. 실측: 헤더 `Deploy` → 팝오버(Not yet / Deploy and finish) → 그 전엔 아무 요청 없음 → deploy → advance(`{"from":"block1_work"}`) → `/study/session`.
- **출구는 하나다 [08-22].** Deploy가 묻고, 배포하고, 다음 단계로 데려간다 — 그 옆의 "I'm done"은 **같은 일을 다른 이름으로** 하는 버튼이었다. 배포는 됐는데 전환이 실패한 경우의 예비로 남겼었는데, 그건 Deploy를 다시 누르면 된다(이미 배포된 것을 배포하는 건 도장을 다시 찍는 것뿐이다).
- **왼쪽 컬럼의 이름은 "Setup" [08-22].** 옆의 두 컬럼은 자기가 뭔지 말하는데(Uncategorized, Conversation) 왼쪽만 이름이 없었고, 스텝 두 개만 오른쪽에 떠 있었다. 이름은 참가자가 이미 들은 단어를 쓴다 — 과제 문장이 "adjust **the setup** so that it responds the way you want"이다. 다른 이름을 붙이면 바꾸라고 지시받은 그것에 두 번째 이름이 생긴다. 두 arm 모두 같은 한 단어다(셸은 arm 간 동일, 다른 건 이 컬럼 *안*뿐).
- **되돌리기/다시하기는 컬럼의 것이지, 열린 카드의 것이 아니다 [08-22].** 두 버튼이 카드 안 Apply 행에 있어서 "이 intent를 되돌린다"로 읽혔다 — 그런데 intent를 지우면 열려 있는 카드는 Uncategorized라, 거기 뜬 undo가 uncategorized 룰에 뭔가 할 것처럼 보이고 실제로는 지운 intent를 되살렸다. 스텝이 다루는 건 **구성 전체**다: 생성·삭제·순서는 어느 카드에도 살지 않고(삭제된 것은 카드 자체가 없다), 한 intent 내부의 역사는 그 카드 안의 Version history가 이미 맡고 있다. 그래서 컬럼 맨 위 자기 줄로 옮겼다.
- **스텝은 어디로 가는지 말한다 [08-22].** `describeStep(from, to)`가 되돌아갈 스냅샷에서 직접 읽어 한 구절로 적는다 — "Undo (⌘Z) — brings back “Complete Text”", "Redo — removes “Complete Text”". 되돌릴 편집이 아니라 **결과**로 쓰는 이유는, 읽는 사람이 지금 누를지 말지를 고르고 있기 때문이다. 없을 때는 사라지지 않고 흐려진다.
- **행에 셰브런은 없다 [08-22].** 행을 **선택하는 것이 곧 여는 것**이라 되돌아갈 닫힌 상태가 없는데, 접힘처럼 생긴 화살표는 접어보라는 초대였고 눌러봐야 아무 일도 안 일어났다. 무엇이 열려 있는지는 행이 켜져 있고 그 아래 에디터가 있다는 것으로 말한다. 점이 화살표가 쓰던 자리로 옮겨가서 모든 제목이 한 자리에서 시작한다 — `+ New intent`의 플러스도 같은 자리다(점이 아닌 유일한 글리프이고, 그게 그 행이 말해야 하는 전부다). 실측: 제목 x가 셋 다 109.
- **스타터 개수는 "가로채는 더미"를 센다 [08-22].** 위에 넣는다는 건 **그 아래 것이 잡던 걸 먼저 가로채겠다**는 뜻이다. 그래서 숫자는 *바로 아래 읽히는 그 더미* 중 몇 개를 가져갈지를 센다 — 로그 전체를 세면 위의 intent가 이미 가져간 것까지 약속했고, 도달 가능한 전부를 세면 대개 uncategorized 더미가 숫자를 지배해서 지금 고민 중인 분할에 대해 아무 말도 안 한다. 실측: 45개 남은 Uncategorized 위에서는 Planning 33 → **18**, 15개를 쥔 Complete Text 위에서는 Planning **6** / Answer a Topic Question 2 / Provide Examples 1. 판정 안 된 질문은 누구 것도 아니므로 어디에도 안 센다 — 그래서 드롭다운의 천장이 행에 적힌 수와 정확히 같다. 그 아래에서도 가져갈 수 있다는 건 폼의 문장이 말한다("and anything below it this also describes") — 그건 먼저 읽히는 것의 *결과*이지 그걸 쓰는 *이유*가 아니다.
- **생성 폼은 리스트의 왼쪽 끝에 선다 [08-22].** 열린 intent의 에디터가 쓰는 들여쓰기 안에 두면 위 행에 딸린 설정처럼 읽힌다 — 실제로는 옆에 새로 쓰이는 형제다. 그래서 행 헤더와 같은 왼쪽 끝, 자기 제목 줄(`● New intent`)을 달고, 들어갈 자리에 그대로 놓인다.
- **폼이 열리면 그 intent가 깎아낼 더미를 화면에 올린다 [08-22].** 가운데 열은 선택된 것을 나열하므로, 선택을 다른 intent에 둔 채 폼만 열면 *다른* 질문 묶음을 보면서 설명을 쓰게 된다. `+ New intent`는 Uncategorized를, 쿼리에서 시작한 경우는 그 질문의 현재 소유자를 선택한다.
- **위치가 아니라 결과를 적는다 [08-22].** "Read before X"는 참이지만 먼저 읽힌다는 게 무슨 뜻인지 이미 아는 사람에게만 쓸모가 있다. 대신 **화면에 보이는 숫자로** 적는다 — "…so any of its **49 questions** can come here. Nothing above it moves." 49는 바로 아래 Uncategorized 행의 49와 같은 수다. 여러 행에 걸치는 합계 하나는 아무 행과도 맞지 않으므로, 이름 붙인 행의 수와 그 아래 전체를 따로 적는다.
- **응답 바에 소유 칩은 없다 [08-22].** 바로 아래에 그 intent의 룰이 통째로 적혀 있다 — 이름은 같은 사실을 덜 유용한 형태로 한 번 더 말하는 것이고, 버전 픽커의 항목에도 이미 들어 있다.
- **룰 상자는 불투명하고 자기 색을 갖는다 [08-22].** 회색 위의 회색은 상자는 보이는데 글자는 안 보인다 — 바뀐 응답을 표시하는 워시 위에 앉으면서 남아 있던 대비마저 잃었다. 카드 배경 + foreground 색 + 12px. 이건 아래 응답을 설명하는 문장이다.
- **표시는 양쪽 거터에서 지불한다 [08-22].** 더하는 패딩만큼 양쪽으로 당겨서, 안의 글자가 다른 응답과 **같은 자리에서 시작하고 같은 자리에서 끝난다** — 룰 상자의 오른쪽 끝이 위 질문 버블과 맞는다(실측 1579 = 1579). 그러려면 자기 폭을 스스로 정해야 해서, decoration이 붙은 메시지에는 ChatMessages가 `w-full`을 안 건다.
- **대화의 색은 답하는 intent의 색이다 [08-22].** 응답의 바와 워시, 그리고 선택된 질문의 링이 전부 그 intent 색이다 — 리스트의 점, 트리의 행, 그리고 여기가 한 색이다. 팔레트가 이름 붙일 수 없는 **데이터에서 온 색**이라 클래스가 아니라 인라인 스타일이고, 워시는 `color-mix`로 그 자리에서 섞는다. 아무 intent도 안 가진 질문은 파랑/보라 그대로다: uncategorized 룰은 다른 어디에도 자기 색이 없다. 실측: 점 `rgb(217,119,6)` = 바 = 링 `#d97706`.
- **바뀐 응답 표시는 박스가 아니라 바와 워시다 [08-22].** 테두리 박스는 내용을 안쪽으로 밀어야 하는데, **응답은 화면에서 제일 긴 것**이라 폭에서 깎인 픽셀이 줄 수로 돌아온다 — 가장 자세히 읽어야 할 그 한 턴이 가장 좁고 길어졌다. 바는 리스트 자기 거터에서 지불한다: 더하는 패딩만큼 왼쪽으로 당겨서 **글자가 다른 응답과 같은 자리에서 시작**하고, 오른쪽에는 아무것도 더하지 않는다. 실측: 왼쪽 1092로 동일, 폭 459 vs 471(거터 12px, 아무것도 줄 맞추지 않는 쪽). 세로 패딩은 24px → 12px. Version history가 현재 행을 표시하는 것과 같은 모양이다.
- **질문을 맨 위에 놓으려면 아래에 놓을 자리가 있어야 한다 [08-22].** 스크롤 위치가 들쭉날쭉했던 건 기억이나 경합이 아니라, **있지도 않은 위치로 스크롤을 요청하면 아무 일도 안 일어나기** 때문이다. 스레드 끝쪽 턴은 아래 남은 내용이 한 화면보다 짧아서 스크롤러가 이미 끝에 가 있고, 같은 클릭이 어떤 질문은 맨 위에, 어떤 질문은 중간에 놓는다 — 차이는 눈에 안 보인다(아래 응답이 우연히 한 화면만큼 기냐일 뿐). 실측: 한 보드에서 여섯은 top+16px, 하나는 200px였고 그 하나는 844px 창에서 아래에 227px만 남아 있었다. 마지막에 **부족분만큼만** 빈 자리를 둔다 — 통짜 한 화면이 아니라, 스트리밍으로 응답이 자라면 다시 맞춰서 내용이 오는 만큼 사라진다.
- **응답을 기다리는 동안 배달된 원본을 세워두지 않는다 [08-22].** 오버라이드가 없다는 건 "배달된 답"이라는 뜻이라, 텍스트가 비면 화면이 원본으로 돌아갔다가 새 답으로 바뀐다 — 룰이 아무것도 안 한 것처럼 보였다가 말을 바꾸는 셈이다. 그래서 기다리는 것도 오버라이드이고, 자리표시자가 답의 자리를 잡고 있는다. 이 판정은 **렌더 시점**에 한다: 효과는 페인트 뒤에 돌기 때문에 질문을 바꾼 첫 프레임에서는 answer가 아직 이전 질문 것이고, 그 한 프레임이 정확히 원본이 비쳤던 자리다.
- **응답은 새 글자가 오기 시작할 때까지 이전 것을 유지한다 [08-22].** 비워 두면 대화가 배달된 원본으로 되돌아가고, 원본이 없는 행에서는 "No reply was delivered for this question"이 apply마다 깜빡였다.
- **sid는 절대 재발급되지 않는다 [08-22].** 예전엔 저장된 스냅샷들의 최대 sid + 1로 추론했는데, apply가 작업 행 하나를 덮어쓰게 되면서 **한 번도 저장되지 않은 채 만들었다 지운 intent는 흔적이 남지 않았다** — 다음 intent가 그 id를 그대로 받고 죽은 intent의 예시·히스토리·판정 캐시를 물려받았다. id는 판정·응답·로그가 전부 매달리는 축이라 "어떤 행이 아직 남아 있나"에 대한 추측일 수 없다. 올라가기만 하는 카운터(`simple_sid_counter`)에서 블록 단위로 발급하며, 기존 과제는 첫 사용 시 네 곳(스냅샷·intent 버전·예시)의 최대값으로 시드한다.
- **삭제는 두 번 묻는다 [08-22].** intent 삭제는 definition·rule·고른 예시·히스토리를 한꺼번에 버리는데 평범한 동사 두 개 옆의 아이콘 한 번이었다. 확인은 **인라인**이다 — 이 보드는 다이얼로그를 열지 않는다(§2).
- **응답 스피너는 실제로 글자가 올 때만 [08-22].** 캐시 히트도, 손대지 않은 rule도 생성 없이 JSON으로 돌아오는데 요청을 보내는 순간 streaming 상태로 두는 바람에, **아무것도 바꾸지 않은 보드에서 질문을 누를 때마다** 스피너가 깜빡였다. 이제 헤더가 도착해 본문이 스트림임이 확인된 뒤에야 그 상태가 된다. 그 전에는 바 자체를 그리지 않는다 — 아래 응답은 아직 원래 것이고, 어느 버전 아래인가에 답이 없다.
- **기본 선택은 Uncategorized [08-22].** 예전엔 전체로 시작했는데 트리에는 거기로 돌아갈 방법이 없다 — **아무도 되돌아갈 수 없는 기본값**이었다. intent가 없는 보드에서는 어차피 같은 60개를 보여준다.
- **스피너는 눌린 컨트롤에 붙는다 [08-22].** 모든 쓰기가 하나의 saving 플래그를 공유해서, 삭제(내부적으로 apply)를 하면 휴지통을 눌렀는데 **Apply 버튼이 돌았다.** 비활성화는 여전히 전역이다 — 동시에 두 개를 쓰게 둘 이유는 없다.
- **입력 상자는 세 줄이 넘어도 잘리지 않을 만큼** [08-22] — WHEN 7.5rem, THEN 9rem에서 시작하고 사용자가 늘릴 수 있다.

- **Version history [08-21].** intent별 히스토리는 카드 안 아코디언이며, 각 행은 직전 버전 대비 **무엇이 움직였는지**를 적는다: `when` · `then` · `when + then` · (최초는) `first`. 읽는 사람이 찾는 게 그것이다 — WHEN이 바뀌면 들어오는 쿼리가 달라진 것이고 THEN이 바뀌면 답이 달라진 것인데, 응답이 달라 보이는 이유는 둘 중 하나뿐이다. 저장하지 않고 앞뒤 행 비교로 계산해 텍스트와 어긋날 수 없게 한다.

- 트리에서 intent 선택 → 그 행이 아코디언으로 펼쳐지며 **인라인 에디터 2개**: ① intent description(When) ② rule(Then). 동시에 보이고 각각 편집 가능.
- **한 번에 하나의 intent만 펼침** [확정].
- 루트 행도 같은 패턴이되 rule 에디터만(루트는 When이 없다).

### 5.3 New intent [확정 — 08-21 개정]

- 모달 없음. 폼은 **그 intent가 들어갈 자리에 그대로 열린다** — 위치를 설명할 필요가 없도록. 대시보드의 나머지는 유지: 쿼리를 보면서 쓴다.
- **주 진입점은 쿼리 행이다 [확정 — 08-21].** 쿼리를 읽다가 "이건 다른 rule을 받아야 한다"고 판단하는 것이 이 보드의 핵심 동작이므로, 생성은 설정 컬럼이 아니라 **그 쿼리에서** 시작한다. 행 호버 시 핀 옆의 `+`.
- **삽입 위치 = 그 쿼리를 지금 소유한 intent의 바로 위** [확정 — 08-21]. 소유자가 없으면(Uncategorized) 리스트 맨 아래. 한 문장이 세 경우(intent 리스트 / Uncategorized / 전체 목록)를 모두 덮으며, 중첩이 주던 **국소성**을 AND 없이 재현한다 — 새 intent는 자기가 파낸 그 intent에게서만 뺏는다.
- **"반드시 포함"은 약속하지 않는다 [확정 — 08-21].** 두 주장을 분리한다: ① *먼저 시도된다* — 위치로 결정론적 보장. ② *내 definition이 그 쿼리에 매치한다* — LLM 판정이므로 보장 불가. ②를 강제하려면 판정을 덮어써야 하고 그것은 §2가 지운 **correction**이며, 워크벤치와 배포 동작을 갈라놓는다. 대신:
  - 출발한 쿼리를 **핀**해서 상단 선반에 고정한다. 선반 행은 다른 행과 같은 소속 칩을 달고 있으므로, **Apply할 때마다 "내 문장이 이걸 잡았나"의 답이 거기 있다.** 새 장치가 아니라 이미 있는 표면이다.
  - 폼에 그 쿼리를 인용해 둔다(맥락이지 제약이 아니다).
- **이름 칸은 없다 [확정 — 08-21 개정].** 다 쓰기도 전에 범주 이름을 물으면 같은 것을 두 번 묻는 셈이다. 쓰는 것은 description 하나. 이름은 ① starter set을 고르면 그 이름이 들어오고 ② 아니면 **저장 뒤에 그 사람이 쓴 문장으로부터 생성**된다(§1 라벨 예외, `lib/study/simple/titles.ts`). 빈칸만 채운다 — 사람이 쓴 이름은 절대 덮어쓰지 않고, 한 번 채운 뒤에는 다시 쓰지 않는다. 트리 행의 **연필**로 언제든 고친다(늘 열려 있는 입력 상자는 스스로 이름 붙는 유일한 항목에 대고 "채워라"라고 말하는 셈이라 쓰지 않는다).
  - 생성된 title은 **모든 버전 행의 빈칸에 채운다.** 최신 행에만 쓰면 "마지막 저장과의 차이" 비교가 아무도 만들지 않은 차이를 찾아내 unsaved로 표시한다.
  - 로그는 `simple_intent_titled` 로 따로 남긴다 — 참가자가 고른 이름과 받은 이름을 분석에서 구분할 수 있어야 한다.
- 에디터 초기값: description은 빈 채, **rule은 그 쿼리가 오늘 받고 있는 rule**(= 현재 소유자의 rule, 없으면 Uncategorized rule)로 채워서 시작한다. 복사이지 상속이 아니다.
- **빈 rule = 시스템 메시지 없음 [확정].** 사용자가 rule을 비웠다면 그것은 사용자의 의도다 — 런타임 폴백을 만들지 않는다.
- Apply/Save → 리스트 추가 + 해당 intent 판정 패스(§6.2) + **방금 만든 intent를 선택 상태로 [08-22]**. 만들고 나서 다음에 보고 싶은 건 "내 문장이 뭘 잡았나"이고 그건 그 intent의 리스트다. 실제 sid는 서버가 배정하므로(폼은 임시 음수를 보낸다) 저장 응답이 `created`로 돌려준다.

### 5.3a Starter set 표시 [확정 — 08-21]

- 쿼리에서 intent를 시작한 경우, Starter sets 드롭다운은 **그 쿼리가 이미 들어 있는 Type/Subtype에 점**을 찍고 드롭다운 상단에 그 점의 뜻을 문장으로 적는다.
- **비용 0.** 클론 프로비저닝 때 준비된 판정을 읽을 뿐이다(실측: 리뷰 60문항 × 템플릿 전부 판정 완료, 모델 호출 0회).
- **분량 적정.** 실측 한 쿼리당 평균 6.2 / 35개(18%, 범위 1–13) — 절반이 켜지는 도배가 아니다.
- **원칙 1 판정:** 통과. 참가자는 지금도 스타터를 하나씩 골라 리스트를 보면 같은 정보를 얻는다. 점은 **클릭 절약**이지 새 능력이 아니다. 단 문구는 사실이어야 한다("이 질문이 들어 있는 세트") — "추천"이면 해석이 되어 위반이다. 체크 표시(✓) 대신 중립적인 점을 쓰는 이유도 같다.

### 5.4 쿼리 리스트와 소속 표시 [확정 — 회신 반영]

- intent 선택 시 중앙 리스트 = **그 intent의 definition에 매치되는 쿼리 전체.** 실제로는 앞선 intent가 가져간(first-match 선점) 쿼리도 **리스트에 보인다.**
- 각 행에 **실제 적용처를 항상 표시**한다: intent 색 점 + 이름, **칠하지 않은 최소 크기**로 [08-22]. 예전엔 리스트에선 채워진 칩이고 응답 위에선 "answered by X" 문장이라, 같은 작은 사실이 두 가지 다른 발표처럼 보였고 문장은 자기가 라벨하는 응답과 경쟁했다. 같은 마크를 두 곳에 쓴다.
- **열려 있는 intent의 definition을 리스트 헤더에 [08-22].** 이 리스트가 무엇의 리스트인지가 왼쪽 카드에만 있으면, "이 문장이 이 질문들을 描述하는가"라는 질문을 두 컬럼에 나눠 놓고 묻는 셈이 된다. 현재 선택 intent가 아닌 곳에 적용 중인 행은 시각적으로 구분하되(회색 처리 등) **경고 아이콘·경고 색은 금지** [확정 — 지도교수 요청]. 이 하나의 규칙이 선점(앞선 형제가 가져감)과 범위 제약(부모 밖 매치) 사례를 모두 중립적으로 덮는다 [제안].
- 뷰어는 항상 first-match의 진실을 보여준다: 그 쿼리에 실제 적용된 rule의 응답 + 적용 출처 마크 + **rule 본문 [08-22]**. 본문은 기본 두 줄로 접고 클릭하면 전문이며, **위의 버전 선택을 따라 바뀐다** — 그게 버전이 뜻하는 바다. rule은 8000자까지 가능해 헤더로는 못 보내고 스트리밍 경로에는 실을 자리가 없으므로, `GET respond`(생성 없이 적용될 rule만)로 따로 읽는다. 캐시 히트와 미스가 서로 다른 경로로 알게 되는 것도 이렇게 하면 없어진다.
- 트리의 intent별 카운트 = **실제 소속(라우팅) 수** [제안] — 매치 수가 아니라 소유 수. 사실 표시이며 진단이 아니다.

### 5.4a Examples와 리스트 순서 [확정 — 08-21, 08-22 개정]

- **intent는 예시 집합으로 대표된다.** 만든 경로와 무관하게 하나의 집합이다: 쿼리에서 파냈으면 **그 쿼리**로 시작하고(이 로그의 실제 질문, 참가자가 직접 고른 것), 맨땅에서 썼으면 모델이 쓴 **3개**로 시작한다. 그 뒤로는 차이가 없다 — **더하고 빼고 다시 쓰는 건 참가자 몫**이고, 앵커는 그 집합의 평균이다.
- **위치는 그 intent의 쿼리 리스트 맨 위.** 전역 핀 선반이 아니다 — 시드를 핀으로 처리했더니 A를 파낸 쿼리가 B를 작업할 때도 남아 있었다. 로그에서 온 예시는 **다른 행과 같은 소속 칩**을 달아서, 다른 intent가 가져간 쿼리를 예시로 넣으면 그 사실이 집합 안에서 바로 보인다.
- **예시 추가는 그 쿼리를 이 intent에 넣는 게 아니다.** 넣는 건 문장이다. 예시가 바꾸는 건 **순서**뿐이고, 순서는 판정이 아니다 — §2가 지운 correction과 갈리는 지점이 여기다.
- **intent 키다 (definition 텍스트 키가 아니다).** 판정·응답 캐시는 텍스트 키라 "고쳤다 되돌리면 공짜"지만, 예시는 문장에서 파생된 게 아니라 **고른 것**이라 문장을 고쳤다고 조용히 버리면 안 된다. 낡는 걸 막는 건 무효화 규칙이 아니라 **Rewrite 버튼**이다(로그에서 온 예시는 남기고 쓴 것만 새로 쓴다).
- **3개 [측정 후 재확정 — 08-22].** 숨겨져 있고 고정일 때는 5개가 더 안정적이었다(평균이라 개수가 많을수록 덜 흔들린다). 예시가 **보이고 편집 가능해지자** 그 근거가 대부분 사라진다 — 먼저 읽는 행이 곧 예시이고, 부르지 않으면 움직이지 않는다. 실측에서 살아남은 것: **평범한 3개는 5개와 거의 같게 정렬한다**(상위 5개 일치 4.3/5로 동일). 살아남지 못한 것: **강한 다양성 요구는 안정성을 반으로 깎으면서**(2.3/5) 실제 다양성은 거의 못 늘린다(0.72→0.62). 좁은 정의에는 퍼질 구석이 없다. 그래서 요구하는 다양성은 구체적인 선까지다 — 표현을 달리하고, 붙여넣은 자료가 있는 것과 없는 것을 섞어라.
- **Closest first / Furthest first 전환 [확정 — 08-22].** 위치는 **Examples 헤더 오른쪽** — 정렬의 기준이 곧 그 예시들이라, 거기 두면 관계가 구조로 드러나고 "아래 리스트는 이것들 기준으로 정렬됩니다" 같은 캡션이 필요 없어진다. **두 선택지를 나란히 두고 현재 것을 채운다**: 문구 하나짜리 버튼은 지금 상태를 *설명*하는 건지 *제안*하는 건지 말하지 못한다. 같은 사실을 반대쪽에서 읽는 것이다. 가까운 순은 "이게 되고 있나"에 답하고, 먼 순은 **"내 문장이 잡은 것 중 내가 뜻한 것과 가장 안 닮은 게 뭔가"**에 답한다 — 다음 intent가 대개 거기서 나오고, 그 행에는 이미 만들기 버튼이 있다. 행마다 라벨을 붙이는 건 해석이라 하지 않는다(§1-4). 전환은 `simple_order_furthest`로 로깅.

### 5.4a-1 정렬의 근거 [확정 — 08-21]

- **문제는 편의가 아니라 신뢰다.** intent를 만들고 열었을 때 **첫 줄이 논쟁의 여지가 있는 쿼리면**, 참가자는 나머지 15개를 보기 전에 "이 분류기는 못 믿겠다"를 배운다(지도교수 지적). 그래서 리스트 순서는 보드가 스스로에 대해 하는 주장의 일부이고, 맨 위는 **가장 이론의 여지가 없는 구성원**이어야 한다.
- 판정은 이 순서를 줄 수 없다 — yes/no라 모든 yes가 똑같다. 그래서 **임베딩 거리** 순이고, 진짜 질문은 *무엇으로부터의 거리인가*다.
  - **참가자가 가리킨 쿼리**(있을 때). 쿼리에서 시작한 intent는 그 쿼리를 기록해 두고(`simple_intent_seeds`), 그걸 앵커로 쓴다. 모델이 만든 무엇보다 낫다 — 이 로그의 실제 질문이고, 그 범주의 주인이 직접 고른 것이다.
  - **가상 질문**(없을 때). definition은 *범주에 대한 서술*이고 쿼리는 *사례*라서 임베딩 공간의 다른 곳에 산다 — 서술 대 실제 질문은 랭킹이 나쁘고, 가상 질문 대 실제 질문은 좋다(HyDE). `+ New intent` 경로에만 필요하다.
- **쿼리 임베딩은 이미 있다** — `score_query_embeddings`, 클론 프로비저닝 때 복사(provision.ts 11단계). 앵커는 definition 텍스트 키로 캐시(`simple_definition_anchors`), 판정·응답 캐시와 같은 방식.
- 생성 시 프롬프트에 **과제 프롬프트**를 넣고, `[Own draft]` `[Assignment prompt]` 같은 **자료 플레이스홀더를 쓸 수 있다고 알려준다** — `buildEmbedText`가 실제 쿼리를 임베딩할 때 붙여넣은 자료를 정확히 그 문자열로 치환하므로 양쪽이 같은 모양이 된다.
- **재배열이지 필터가 아니다.** 리스트에 무엇이 있는지는 판정이 정하고(§5.4), 순서만 여기서 정한다. 조용히 하나라도 빠지면 보드가 "이 문장이 무엇을 잡는가"에 대해 거짓말을 하게 된다. 소유한 것 먼저, 그다음 앞선 intent가 가져간 것 — 각각 순위대로.
- **예시 개수는 5개 [측정으로 확정 — 08-21].** 앵커가 예시들의 평균이라 개수는 사실 분산 문제다: 같은 definition을 두 번 생성했을 때 리스트 맨 위가 얼마나 움직이는가. 정의 3개 × 생성 3회로 60문항을 정렬해 보면 — **3개일 때** 3개 중 2개에서 첫 줄이 실행마다 바뀌었고, 최악의 경우 상위 5개가 실행 간 **2.3/5**만 일치했다. **5개일 때** 첫 줄이 바뀐 건 1개, 같은 최악 케이스가 **4.3/5**로 올랐다. 8·12는 5보다 나아지지 않았다(최악 케이스 4.0·3.5, 4회 실행의 잡음 범위). 곡선의 평평한 지점이 5다.
- **화면 라벨은 "Examples" 한 단어.** "When a question…" 아래의 Examples는 그런 질문들의 예시라는 뜻으로 그대로 읽힌다. 출처와 성격을 설명하는 세 문장이 붙어 있었는데, 그건 읽는 사람이 필요해서가 아니라 쓰는 쪽이 기능에 대해 불안할 때 쓰는 종류의 주석이다.
- **§1 판정:** 생성된 질문은 설정이 아니다 — 판정에도 응답에도 안 들어가고, 스냅샷에 저장되지 않으며, 편집할 수 없다. **다만 화면에 펼쳐 두지 않는다**: definition 옆에 "당신 설명이 포괄하는 질문들"이 상시 떠 있으면 그건 수렴 대상이 될 초안이고, 기계가 쓴 텍스트로 수렴하는 것이 §2가 지운 propose 루프다. **접어 두고 한 번의 클릭으로 열며, 여는 행위를 로깅**(`simple_examples_open`)해서 분석에서 분리 가능하게 한다.

### 5.4b 검색 [확정 — 08-21, §2에서 복원]

- 중앙 리스트 헤더에 **일반적인 검색창**. 없으면 "가장 기본적인 것이 없다"는 말이 나온다.
- **학생이 쓴 말만** 검색한다. 응답은 생성물이라 rule이 바뀔 때마다 결과가 움직이고, intent 제목은 참가자 자신의 라벨이라 여섯 개 리스트에서 눈으로 찾는다.
- **현재 선택 안에서** 거른다 — 헤더가 보여준다고 말한 그 목록이 대상이다. 조용히 주제를 바꾸는 상자는 없는 것보다 나쁘다. 대신 **여기 없으면 로그의 다른 곳에 몇 개 있는지 말한다** — "여기 없음"이 "어디에도 없음"으로 읽히면 안 된다.
- 매치는 학생의 말 안에서 **하이라이트**한다. 자료 태그는 안 한다 — 태그는 화면에 없는 텍스트를 대신하므로, 거기 표시하면 보이는 것에서 찾았다고 주장하게 된다.
- **연구 쪽 유의 [확인].** 검색은 Baseline에서는 순수 이득이지만(달리 찾을 방법이 없다) SCORE에서는 intent가 하는 일의 일부를 대신한다 — 즉 **두 조건의 격차를 좁힐 수 있다.** definition은 여전히 *배포되는 것*이고 검색은 *보는 것*뿐이라 무너지지는 않는다. 타이핑이 멎으면 `simple_search`로 로깅해 분석에서 통제 가능하게 한다.

### 5.2a Undo / Redo [확정 — 08-21]

- **이번 세션에 apply한 것들에 대한 되돌리기/다시하기.** 워드프로세서의 그것과 같은 성격 — 지금 하고 있는 편집을 되돌린다. 오래된 상태로 가는 지속적인 길은 히스토리다.
- **비용 0.** apply된 모든 wording은 자기 텍스트 해시로 판정이 저장돼 있어서, 되돌아가면 모델 호출 없이 다시 붙는다.
- **되돌리기는 rewind가 아니라 apply다.** 여기서는 최신 행이 곧 설정이므로, 오래된 행을 조용히 최신으로 만들면 트레일이 일어나지 않은 일을 말하게 된다. 그래서 undo도 하나의 write이고 히스토리에 그렇게 남는다. `simple_undo` / `simple_redo`로 로깅 — 무엇이 일어났는지는 apply 기록이 이미 갖고 있고, 이 둘은 *편집이 아니라 이동으로 거기 도달했다*를 말한다.
- **위치는 설정 컬럼(sticky)이지 에디터 안이 아니다.** Apply 옆에 뒀더니 undo가 마지막 intent를 지우면서 버튼을 담고 있던 카드까지 같이 사라졌다 — **되돌리는 컨트롤이 되돌릴 대상 안에 살 수는 없다.**
- 단축키 ⌘Z / ⇧⌘Z. 텍스트 상자 안에서는 그 상자의 것이므로 가로채지 않는다.

### 5.5 소속 diff [철회 — 08-22]

- 초록/빨강 행 표시는 **제거했다.** 그 신호는 **위치로 읽히는 것**이었다 — 리스트가 로그 순서로 고정돼 있을 때 "이것들이 움직였다"로 읽혔다. §5.4a의 예시 기준 정렬과 방향 전환이 들어오면서 들어온 행이 어디에 있을지 알 수 없게 되어, 위치로 읽는 신호를 위치가 고정되지 않은 리스트에 얹는 꼴이 됐다. 행 하나가 이미 참가자 토큰·턴·소속 마크·자료 칩·검색 하이라이트를 달고 있는 것도 있고.
- 서버의 `diffFrom` 계산도 함께 제거했다(반쯤 연결된 기능은 썩는다).
- **다시 필요해지면**: 재정렬을 견디는 형태는 행 색이 아니라 **헤더의 개수**("3 들어옴 · 1 나감")다 [제안].

## 6. 속도 사양 — 이 버전의 존재 이유

### 6.1 체감 규칙

- **저장은 어떤 LLM 호출도 기다리지 않는다** — 판정·응답·이름 생성 전부 저장 후 비동기.
- 캐시 히트 상태의 전환(버전·intent·대화 전환)은 스피너 없이 즉시.
- 실패는 행 단위 재시도로 국소화 — 전역 실패 상태를 만들지 않는다.

### 6.2 판정 (When, SCORE만)

- **판정 캐시 키 = (쿼리, definition 텍스트).** 트리 위치·순서·pin은 키에 넣지 않는다. 귀결: **intent 하나의 definition을 고치면 그 intent만 재판정**되고 나머지는 전부 캐시 히트, 재정렬·트리 이동은 LLM 비용 0.
- 재판정 패스는 병렬·백그라운드로 돌고, 결과 도착 순으로 리스트·카운트를 스트리밍 갱신한다(per-intent 진행 표시). N≈100에서 수 초 내 완료를 실패 기준(하한)으로 [제안] — 목표는 §6.4.
- 판정 등급을 내부적으로 몇 단계로 두든, **노출은 소속 여부(와 적용처)만** [확정 — 판정 큐·등급 표면 없음].

### 6.3 응답 (Then, 양 조건)

- **스트리밍은 스크롤을 건드리지 않는다 [08-22].** 하이라이트된 메시지를 화면에 들여오는 이펙트가 `messages`를 의존성으로 갖고 있어서, 토큰이 들어올 때마다 다시 스크롤을 끌어왔다 — 아래를 읽으려는 사람을 계속 되돌린다. 이제 **메시지가 바뀔 때 한 번만** 들여온다(id 기준 ref). 첫 렌더에는 대상이 아직 DOM에 없으므로 `messages` 의존성 자체는 유지해야 한다.

- **응답 캐시 키 = (쿼리, 그 쿼리에 적용되는 rule 텍스트)** [제안] — 버전 번호가 아니라 적용 텍스트 기준. 귀결: SCORE에서 intent A의 rule만 고치면 **A 소속 쿼리만** 재생성 대상이고 나머지는 캐시 히트. Baseline은 프롬프트 전체가 한 텍스트이므로 수정 시 전 쿼리가 재생성 대상 — **이 비대칭은 성능 버그가 아니라 조작(수정의 국소성) 그 자체다. 숨기지 말 것.**
- **lazy + 프리페치** [확정 + 제안]: 뷰어 열람 시 캐시 미스면 스트리밍 생성(첫 토큰 ≤ 2초 목표). Save 직후 백그라운드 프리페치 우선순위 — ① 현재 펼친 intent 소속(SCORE) / 리스트 상단 N개(Baseline) ② pinned ③ 최근 열람. 전량 사전 생성은 전제하지 않는다(§3.2).
- **모델 패리티 [제안 — 중요]:** 응답 생성은 풀 버전의 학생 런타임과 **동일 모델·동일 컨텍스트 경로**를 쓴다. 시뮬레이션이 배포 행동을 대표해야 하므로 속도를 위해 여기서 모델을 낮추지 말 것 — 속도는 캐시·프리페치·병렬로 번다.
- 판정은 경량 모델, 버전 이름은 초경량 모델. LLM 동시성 리미터는 기존 것을 공유.

### 6.4 실측과 최적화 [확정 — 회신 반영]

- **성능 기준은 "최대한 빠르게"다.** 위 수치들은 달성 목표가 아니라 실패 기준(이보다 느리면 설계 재검토)이다.
- 구현 후 **성능 실측 리포트**를 작성해 연구자와 최적화를 상의할 것. 측정 항목:
  1. 판정 패스 완료 시간 (intent 1개 재판정, 실제 데이터셋 N 기준)
  2. 응답 첫 토큰·완료 지연 (캐시 미스 시)
  3. 캐시 히트 전환 지연 (버전·intent·대화 전환)
  4. Save → UI 반영 지연
  5. 프리페치 적중률 (뷰어 열람 시점의 캐시 히트 비율)
  6. 동시성 한도에서의 병목 지점
- 개선 후보(병렬도 상향 · 프리페치 범위 확대 · 판정 배칭 · 스냅샷 사전 컴파일 등)는 실측 수치와 함께 제안할 것.

## 7. 로깅

행동 기록이 RQ1(조직·저작 행태) 분석의 원천이다. 최소 다음을 서버 측에서 적재 [제안]:

| event | payload 요지 |
|---|---|
| `simple_version_save` | condition, versionNo, 대상(prompt/root/intentId), diff 요약(필드·±자수) |
| `simple_version_restore` | from→to, 소실 버전 수 |
| `simple_version_switch` | global 또는 local, from→to, conversationId(local일 때) |
| `simple_intent_create` / `update` / `delete` | intentId, 변경 필드(desc/rule), 부모/순서 |
| `simple_intent_reorder` / `move` | intentId, from→to |
| `simple_intent_expand` | intentId |
| `simple_pin_add` / `remove` | messageId |
| `simple_response_view` | messageId, versionNo, cacheHit 여부 |

**스터디 전 커버리지 검증 필수** — 과거에 "스펙에만 있고 미구현인 이벤트"가 분석 계획을 무너뜨린 전례가 있다. 분석은 실제 적재되는 표를 기준으로 한다.

## 8. 구현 노트

- **별도 조건 쌍으로 추가** [확정]: 풀 버전 코드·조건은 그대로 보존. condition 값에 Simple 쌍을 추가하고(명칭 예: `simple_score` / `simple_baseline` [제안]) 기존 참가자·클론·배정 기계를 재사용.
- **참가자 대면 명칭·문구는 시스템 리포에서 기결정된 값을 쓴다** [확정]. 헤더 칩 문자열은 설정 가능해야 한다(논문 그림 렌더링 시 교체 요건 계승).
- **미노출이지 삭제가 아니다**: 지능 기능은 Simple 모드에서 렌더·라우트 게이트로 차단. 단, Simple 화면에 죽은 진입점(빈 버튼·고아 메뉴)이 남으면 안 된다 — 없는 기능은 **부재(빈 자리)**로 읽혀야 한다.
- **재사용 힌트** (08-05 as-built 기준 명칭 — **최신이 아닐 수 있음**, 현행 코드에서 대응물 확인): definition 텍스트 키 판정 캐시(defHash) · Baseline 프롬프트의 rule-홀더 저장 기제(prompt_holder) · 응답 프리뷰 캐시(score_rule_previews) · 대화 요약 컨텍스트(digest) · 클론/배정(study_clones.condition) · 이벤트 적재(study_events) · 체인 컴파일/라우팅(compileChains/resolveRoute). 대응물이 없거나 달라졌으면 이 문서의 의미론을 기준으로 새로 구현.
- **스코프 규율**: 이 문서에 없는 기능을 추가하지 말 것(특히 AI 보조의 부활). 애매하면 §1-1의 질문으로 판정하고, 그래도 애매하면 §9에 질문을 추가하고 멈출 것.
